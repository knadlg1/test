# 마마파파 (가칭) 기획서 v0.1

## 1. 한 줄 정의
스마트폰이 어려운 부모님·조부모님(대상자)을 **TV로 가족과 연결**하고, 정기 방문과 소일거리로 외로움과 건강을 돌보는 가족 단위 플랫폼.

## 2. 핵심 원칙
1. **대상자는 배우지 않는다.** 조작은 가족이 대신하고, 어르신 쪽 조작은 *없거나 버튼 1개*.
2. **TV가 접점이다.** 폰이 아니라 익숙한 TV를 쓴다.
3. **안정성이 기능보다 먼저다.** 안 켜지거나 끊기면 어르신은 다시 쓰지 않는다.
4. 가족이 안심할 수 있어야 한다. (잘 받으셨는지, 봤는지 확인)

## 3. 사용자
| 구분 | 설명 | 사용 기기 |
|---|---|---|
| 대상자 | 부모님·조부모님. 기계 조작 어려움 | TV + 전용 박스 + 리모컨 |
| 가족 | 자녀·손주 등 초대된 구성원 | 스마트폰 앱 |

## 4. 3대 기능과 단계
| 단계 | 기능 | 성격 |
|---|---|---|
| **1단계 (지금)** | ① TV 가족 연결: 사진·영상 초인종 재생, 자동 다시보기 알림, TV 영상통화 | 소프트웨어 + 하드웨어 |
| 2단계 | ② 방문 말벗 케어: 정기 방문, 건강·투약 체크, 가사 | 오프라인 운영 사업 |
| 3단계 | ③ 정기배송 소꿉놀이: 어르신 소일거리 키트 | 물류·콘텐츠 사업 |

2·3단계는 1단계의 가족 구성·구독·어르신 댁 정보를 공유하므로, 1단계 데이터 모델에 **가족/대상자/주소/구독** 개념을 처음부터 넣는다.

## 5. 기능 ① 상세

### 5.1 어르신이 보는 화면 (버튼 1개 원칙)
| 상황 | TV 동작 | 어르신 조작 |
|---|---|---|
| 가족이 사진/영상 업로드 | 필요하면 TV를 켜고 전체 화면에 자동 재생. 화면에 "○○가 보냈어요" 표시 | **없음** |
| 재생 끝 | 자동으로 대기 화면(최근 사진 슬라이드)으로 복귀 | 없음 |
| 다시보기 | 일정 주기에 "다시 보시겠어요?" 팝업 | 버튼 1개(확인) = 재생, 무시 = 자동 닫힘 |
| 영상통화 수신 (2단계 구현) | 전체 화면 벨소리 + "○○가 전화했어요" | 버튼 1개(받기) |

- 버튼은 리모컨 아무 키나 눌러도 되게 한다. (OK 키 한정 X)
- 메뉴, 로그인, 설정 화면은 어르신에게 노출하지 않는다.
- 글자·버튼은 아주 크게, 한 화면에 한 가지 일만 한다.

### 5.2 가족이 쓰는 앱
- 가족 초대 (링크/코드), 대상자 등록
- 사진·영상 업로드 → 전송
- 상태 표시: 전달됨 / 재생됨 / 시청함 (안부 신호 역할)
- 영상통화 걸기 (후속 단계)

## 6. TV 연결 방식 비교 (안정성이 최우선)

| 방식 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **A. 전용 안드로이드 TV 박스/스틱을 HDMI에 연결 (권장)** | 스마트 TV 여부 무관(HDMI만 있으면 됨). 우리가 OS·앱 버전을 통제. 부팅 시 앱 자동 실행(키오스크). HDMI-CEC로 TV 전원·입력 전환 가능. 원격 업데이트·모니터링 | 하드웨어 구매·배송·초기 설정 비용. TV 제조사별 CEC 동작 차이 | 1순위 |
| B. 스마트 TV 자체 앱 (삼성 Tizen, LG webOS 등) | 별도 기기 불필요 | 제조사마다 개발 따로. 오래된 TV는 미지원. 꺼진 TV를 앱이 깨우기 어려움. 앱 심사·업데이트 제약 | 보조 옵션 |
| C. 폰에서 TV로 캐스팅 | 구현 쉬움 | 누군가 어르신 댁에서 조작해야 함 → 목적에 반함 | 제외 |

**권장: A.** 박스를 미리 설정해 보내면 어르신 댁에서는 *전원 + HDMI 연결*만 하면 된다.

안정성 확보 방안:
- 박스는 항상 켜 둔 대기 상태, 부팅 시 앱 자동 실행, 앱이 죽으면 자동 재시작.
- 서버와 상시 연결(푸시 + 재연결 로직), 박스가 주기적으로 상태 신호를 보내고 끊기면 가족에게 알림.
- 영상은 박스에 **미리 내려받아** 재생해서 재생 중 끊김을 줄인다.
- 와이파이: 초기 설정은 가족 폰으로 QR 스캔 방식을 검토. 유선 LAN 지원도 고려.

**주의/미검증 사항**
- HDMI-CEC로 꺼진 TV를 켜고 입력을 전환하는 동작은 TV 브랜드별로 다르다. 실제 TV 몇 종으로 **반드시 시제품 테스트**가 필요하다.
- 영상통화는 TV 쪽에 **카메라와 마이크**가 필요하다. 박스에 USB 웹캠을 같이 보내야 하며, 가장 큰 기술·비용 요소라 2단계로 미룬다.

## 7. 시스템 구성 (초안)
```
[가족 앱] --업로드--> [서버: 인증/가족/미디어/알림] --푸시--> [TV 박스 앱]
                              |                               |
                        [미디어 저장소]                  [HDMI-CEC로 TV 켜기]
```
- 가족 앱: 폰 (크로스플랫폼 or PWA 중 선택 필요)
- TV 앱: 안드로이드 TV 앱
- 서버/저장소: 클라우드 관리형 서비스 사용 (인프라 직접 운영 최소화)

## 8. 로드맵
1. **기획 확정** ← 현재
2. 프로토타입 검증: TV 박스 1종 + TV 2~3종으로 "업로드 → TV 자동 켜짐 → 재생" 확인 (가장 큰 리스크 먼저 검증)
3. 가족 앱 + 서버 MVP: 초대, 업로드, 상태 표시
4. 다시보기 알림, 안정성(재연결·모니터링)
5. 영상통화 (카메라 하드웨어 포함)
6. 방문 케어, 소꿉놀이 (별도 기획)

## 9. 결정 사항
- 파일럿: 창업자의 할머니 댁 1곳 (과금·다중 가정 기능은 파일럿 범위 밖)
- 사업 모델: 최초 구독 시 박스·설치비를 일시 부과 + 월 운영 구독비 별도
- 가족 앱: 초기에는 웹앱(PWA)으로 시작해 피드백 속도 확보
- TV 연결: 전용 안드로이드 TV 박스를 HDMI로 연결 (TV 기종 무관, HDMI 단자가 있는 모든 TV 대상)

## 10. 미결정 사항
- 할머니 댁 TV 기종, 셋톱박스(케이블/IPTV) 사용 여부, 남는 HDMI 포트 유무, 와이파이 유무
- 사진·영상 보관 기간과 개인정보 정책 (가족 사진은 민감 정보)

## 11. 용량·비용·이식성 설계 원칙 (처음부터 적용)
미디어 저장·전송이 대규모에서 비용의 대부분이 되므로 1단계부터 지킨다.

### 11.1 업로드 시 용량 줄이기
- 원본을 그대로 저장하지 않는다. 업로드 → 임시 저장 → 변환 작업(서버, ffmpeg) → 압축본 저장 → 원본 삭제.
- 사진: 긴 변 1920px 이하, 품질 약 80%로 재인코딩 + 썸네일 생성.
- 영상: 720p, H.264, 약 2Mbps 목표 + 썸네일. TV 화면에는 720p로 충분.
- 업로드 상한: 영상 길이·파일 크기 제한(초기값은 파일럿에서 조정).

### 11.2 저장·보관
- 가구 단위 용량 한도를 구독 요금제와 연결한다.
- 오래된 미디어는 저렴한 저장소로 이동하거나 가족이 내려받도록 안내한다. 기간은 개인정보 정책과 함께 결정.
- 동일 파일 중복 업로드는 해시로 감지.

### 11.3 전송
- TV 박스는 1회만 내려받아 로컬에 저장하고 다시보기는 로컬에서 재생.
- 가족 앱 목록은 썸네일만 로드, 원본은 선택 시에만 내려받기.

### 11.4 이식성 (벤더 종속 줄이기)
- 파일 저장소는 S3 호환 API로만 접근하고, 앱 코드는 얇은 저장소 계층을 통해 사용한다.
- DB는 표준 SQL(Postgres)만 사용한다. 벤더 전용 기능에 비즈니스 로직을 넣지 않는다.
- 사용자 ID는 자체 ID를 기준으로 하고 인증 서비스 ID에 직접 의존하지 않는다.
- 변환 작업은 별도 워커로 분리해 어느 클라우드에서도 실행 가능하게 한다.
